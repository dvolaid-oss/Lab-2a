# תיעוד הריפו: Lab 2a (בעברית)

המסמך הזה מסביר מה יש בריפו, איזה מקרה נבחר ולמה, ומה נמצא בכל תיקייה וקובץ. הוא כתוב כך שגם מי שלא מכיר את התחום יבין.

---

## 1. על מה המטלה?

בארגונים יש **SOC**, צוות אבטחה שמנטר את פעילות המחשבים ומחפש התקפות. היום מערכת AI עוזרת לצוות: היא מזהה פעילות חשודה וממליצה מה לעשות, למשל "לנתק את השרת מהרשת".

**המטרה של Lab 2a:** לשחק תפקיד של אנליסט, **לא לקבל אוטומטית** את מה שה-AI אומר, לבדוק את הראיות לבד ולקבל החלטה מנומקת.

המערכת שהקורס סיפק נקראת **Morpheus Lite**. כל הנתונים בה מזויפים (סינתטיים), ואף מערכת אמיתית לא נפגעה.

---

## 2. איזה נושא (מקרה) בחרתי?

המערכת יצרה **63 התראות**. המרצה לא הקצה מקרה מסוים, ולכן בחרתי **שני מקרים**:

### מקרה ראשי: `alert-0-17` (סיכון 100)
| שדה | ערך |
|---|---|
| משתמש | `svc-backup` (חשבון השירות של הגיבויים) |
| שרת | `db-01` (שרת מסד הנתונים) |
| מה קרה | 23 ניסיונות התחברות כושלים, ו-48MB של מידע שיצאו החוצה |
| מאיפה | כתובת IP באיראן (`91.240.118.9`) |
| המלצת ה-AI | לבודד את השרת, באישור אדם |
| **ההחלטה שלי** | **`escalate`**: להעביר לדרג גבוה יותר |

**למה escalate?** זה נראה כמו התקפה אמיתית, אבל **כל הראיות מגיעות משורת לוג אחת**, בלי אימות ממקור נוסף. ניתוק שרת מסד נתונים הוא צעד עם השפעה גדולה על הארגון, ולא אנליסט יחיד צריך להחליט עליו.

**למה דווקא המקרה הזה?** הוא היה המקרה הראשון שסומן "REVIEW REQUIRED", כלומר דורש אישור אנושי לפי חוקי ה-RAI.

### מקרה להשוואה: `alert-0-0` (סיכון 80)
גישה רגילה לקובץ ממחשב פנימי. **ההחלטה: `reject`**, כי זו התראת שווא. בחרתי אותו כדי לא להתמקד רק במקרה המסוכן ביותר, כמו שהמדריך ממליץ.

### הממצא המרכזי
**כל 63 האירועים הפכו להתראות**, גם האירועים הנורמליים. הסיבה: המערכת "למדה" את התנהגות המשתמשים רק בשעה 06:00 בבוקר, וההרצה הייתה ב-07:00, אז שעת הכניסה של כולם נראתה חריגה. ה-**Meta-AI**, שתפקידו לתפוס טעויות כאלה, **אישר את כל 63 המקרים** בלי להעיר.

**הלקח:** AI יכול להישמע בטוח בעצמו ולעמוד בכל החוקים, ועדיין לטעות.

## 5. מילון מונחים

| מונח | הסבר פשוט |
|---|---|
| **SOC** | Security Operations Center, צוות שמנטר אבטחה |
| **Telemetry** | נתוני פעילות של מחשבים (לוגים) |
| **Kafka / Redpanda** | "דואר" בין חלקי המערכת. כל חלק שולח ומקבל הודעות דרכו, וכל הודעה נשמרת |
| **Topic** | "תיבת דואר" בתוך Kafka לסוג מסוים של הודעות |
| **Isolation Forest** | אלגוריתם למידת מכונה שמזהה אירועים חריגים |
| **Fingerprint / z-score** | "טביעת אצבע" של ההתנהגות הרגילה של משתמש. ה-z-score מודד כמה אירוע חורג ממנה |
| **XAI** | Explainable AI: מסביר **למה** ה-AI המליץ על משהו |
| **RAI** | Responsible AI: בודק אם הפעולה **מותרת** ואם היא דורשת אישור אדם |
| **Meta-AI** | בודק אם ההערכה של ה-AI **אמינה** ונתמכת מספיק |
| **alert_id** | מזהה של התראה (למשל `alert-0-17`) |
| **correlation_id** | מזהה שמקשר את כל ההודעות של אותו אירוע, מהלוג הגולמי ועד ההחלטה |
| **Audit trail** | תיעוד מלא של מי החליט, מה ולמה |

### 5 ההחלטות האפשריות
| החלטה | מתי בוחרים בה |
|---|---|
| `approve` | הראיות מספיקות לאשר את המלצת ה-AI |
| `reject` | ההמלצה שגויה או מוגזמת |
| `escalate` | המקרה חורג מהסמכות שלי, ומעבירים למנהל |
| `request_more_evidence` | יש סיכון, אבל חסרות ראיות |
| `defer` | אין צורך בפעולה עכשיו, ממשיכים לעקוב |
